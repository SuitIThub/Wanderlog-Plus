# Geschätzte Tageszeiten Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Zeiten der Tagesplanung werden aus Reihenfolge, Wegen und Aufenthaltsdauer geschätzt; nur ausdrücklich feste Zeiten bleiben beim Ort.

**Architecture:** Neue Felder `DayItem.fixedTime`/`stayMinutes` und `Day.startTime` (shared); ein reiner Schätzer `DaySchedule` in shared rechnet über `DayFlowView` und liefert pro Programmpunkt Start/Ende/Warnungen. `DayNow` (Heute, Widgets, „Was jetzt?“), `GuideMatch`, die Zeitleiste und der Chat-Server lesen nur noch den Schätzer bzw. `fixedTime`; `DayItem.time` wird nirgends mehr gelesen.

**Tech Stack:** Kotlin, Compose (Robolectric-Tests), Ktor-Server, kotlinx.serialization.

**Spec:** `docs/superpowers/specs/2026-11-16-day-times-design.md`

## Global Constraints

- `DayItem.time` bleibt im Modell, wird aber von keinem Code mehr als Zeit gelesen (nur noch alte Daten). Keine Migration.
- Tagesbeginn ohne Einstellung: 09:00 (`DaySchedule.DEFAULT_START = 9 * 60`).
- Anzeige: geschätzt „~HH:mm“, fest „HH:mm“ mit Stecknadel-Icon (`Icons.Filled.PushPin`).
- Warntexte exakt: „~N Min zu spät“, „bei Ankunft geschlossen“, „Zug knapp“ (bei Flug „Flug knapp“).
- Startkarte: „ab HH:mm“ als Zusatz zum Untertitel.
- Sheet-Titel „Zeit & Dauer“, Menüeintrag „Zeit & Dauer“, Schalter „Feste Uhrzeit“, Dauer in Schritten ±15 Min, „Zurücksetzen“.
- Chat: eine Plan-Zeit ist immer eine feste Zeit; die KI setzt sie nur für echte Termine.
- Version 0.76.0, versionCode 97, CHANGELOG-Abschnitt.
- Build: `export JAVA_HOME="/c/Program Files/Eclipse Adoptium/jdk-21.0.8.9-hotspot"`; Gesamtlauf `./gradlew :shared:test :client:test :server:test :app:testDebugUnitTest`.

**Ruling vs. Spec:** Statt eines neuen Felds `ChatPlanStep.fixed` bedeutet `ChatPlanStep.time` ab jetzt „feste Zeit“ (Tool-Beschreibung sagt das der KI). Gleiches Verhalten, ein Feld weniger; Kosten falls falsch: ein zusätzliches Feld nachrüsten.

## Review Focus

1. Transit-Abfragen eines Wegs hängen an der geschätzten Abfahrtszeit, die wieder von der Wegdauer abhängt → kein Flackern/Endlosladen: die Abfahrtszeit für Abfragen wird auf die volle Stunde abgerundet (Test in Task 4).
2. Tag ohne Unterkunft am Morgen (Anreisetag): Uhr startet beim Tagesbeginn am ersten Ort, ohne Weg (Test in Task 2).
3. Feste Zeit früher als die geschätzte Ankunft eines späteren Punkts (falsche Reihenfolge) → nur `LATE`, nie Umsortieren (Test in Task 2).
4. Ungültiges `fixedTime` („25:99“, „“) → gilt als nicht fest (Test in Task 2).
5. Alte Daten mit `time` aber ohne `fixedTime` → werden geschätzt, die alte Zeit erscheint nirgends (Test in Task 4).

- Produces:
```kotlin
enum class TimeWarning { LATE, CLOSED, MISSES_RIDE }
data class ScheduleWarning(val kind: TimeWarning, val minutes: Int = 0)
data class ScheduledStop(val itemId: String, val start: Int, val end: Int, val fixed: Boolean,
    val wayMinutes: Int?, val wayMode: TravelMode?, val warnings: List<ScheduleWarning>)
data class DayScheduleView(val dayStart: Int, val stops: Map<String, ScheduledStop>) {
    fun startText(itemId: String): String?   // "~13:00" / "13:00"; null für Notizen
}
object DaySchedule {
    const val DEFAULT_START = 9 * 60
    fun build(flow: DayFlowView, places: Map<String, Place>, saved: List<SavedPlace>, day: Day?, dow: Int?,
        endpoint: (Endpoint) -> Pair<Double, Double>? = { e -> e.lat?.let { la -> e.lng?.let { la to it } } },
        known: (legKey: String) -> Int? = { null }): DayScheduleView
    fun forDate(date: String, day: Day?, items: List<DayItem>, flights: List<Flight>, trains: List<Train>,
        stays: List<Stay>, saved: List<SavedPlace>, places: Map<String, Place>, regions: List<Region>,
        endpoint: (Endpoint) -> Pair<Double, Double>? = …, known: (String) -> Int? = { null }): DayScheduleView
}
```
  `dow`: 0 = Sonntag, null = Öffnungszeiten nicht prüfen. `forDate` baut `DayFlow.build(date, items, movementsOn(flights, trains, date), …)`, `dow` aus `date`.

Algorithmus (über `flow.entries` in Reihenfolge; `clock` = Minuten, `at` = letzter bekannter Punkt):
- `Start`: clock = `day.startTime` (gültig) ?: DEFAULT_START, at = Unterkunft. Fehlt `Start`, beginnt clock beim ersten Item mit Weg 0.
- `Item` (PLACE): Weg = `known(leg.key)` ?: Dauer der gewählten Verbindung (`item.legTransit`) ?: `DayNow.way(km, item.legMode)` von `at` (nur wenn `flow.legTo(idx)` existiert, sonst 0). arrive = clock + Weg. fest (`DayNow.mins(fixedTime)` != null) → start = fixed, `LATE(arrive - fixed)` wenn arrive > fixed; sonst start = arrive. end = start + (`stayMinutes` ?: `DayNow.stayMinutes(place, saved)`). `CLOSED` wenn `dow != null` und `isOpenAt(place.openingPeriods, dow, hhmm(start)) == false`. clock = end.
- `Item` (NOTE): keine Zeit, kein Eintrag.
- `Ride`: Weg zum Abfahrtsort analog (Modus aus `day.legs[key]?.mode`); dep = `mins(movement.time)`; wenn dep != null und clock + Weg > dep → `MISSES_RIDE` am letzten Stop davor (falls vorhanden). clock = Ankunft (gleicher Tag) ?: dep ?: clock; at = Ankunftsort.
- `Night`: ignorieren.
